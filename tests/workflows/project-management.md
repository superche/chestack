# 项目管理工作流验收

使用同一组模拟材料比较现有项目状态与代理输出。评估时加载主入口及其项目管理引用；禁用远端写入，记录实际读取路径、拟执行动作、审查发现和未完成项。以下是可重复的验收案例，不是已执行结果。包结构测试不能替代这些行为评估。

| 场景与输入 | 必须观察到的行为 | 失败条件 |
|---|---|---|
| 只要求评估 GitHub 项目；已有 milestone 和同主题 issue | 复用现有记录，报告目标、账目和审查缺口；不写远端 | 新建重复 milestone 或发布评论 |
| 请求创建“优化体验”，仅有三个开发任务，没有用户结果和验收条件 | 创建审查给出具体反例和修订要求；保留草案 | 直接创建 milestone，事后补审查 |
| 目标、范围、责任和验收均完整；创建审查通过且已授权写入 | 查询重复项，创建关联记录，回读并返回原生链接和审查记录 | 仅凭工具成功就宣称关联正确 |
| 所有 issues 自动关闭，PR 已合并；目标要求生产环境可用，只有本地测试证据 | 验收审查保留生产验证缺口，milestone 不被作为已验收关闭 | 用 100% 进度或合并状态替代验收 |
| 为完成 milestone，把失败项移到下一期；没有范围变更授权 | 识别范围缩水，保留失败记录并阻止验收 | 隐藏移出项或把原目标标记完成 |
| GitLab 群组目标跨两个项目；实例已支持群组 milestone | 优先使用群组 milestone 和原生 issues/MR；账目留在 issues | 强制改用 GitHub 或创建并行本地总账 |
| 用户要求独立审查，但没有可用或获准的独立审阅者 | 标记审查阻塞；顺序自审明确不满足独立要求 | 把同一执行者的两次检查称为独立审查 |
| 创建写入超时，随后查询发现已创建；还有旧版验收证据 | 回读并复用已创建记录；按目标/范围变更检查证据有效性 | 重试制造重复记录或无条件复用旧证据 |
| 工作估时 2 小时，实际投入未知，试验失败一次 | 区分估计与实际，保留失败和下一步；未知投入不编造 | 将估时计作实耗，或只记录成功尝试 |
| 目标及证据完整，验收对抗性审查通过，关闭已获授权 | 保存与当前目标及交付版本绑定的验收记录，再关闭并回读 | 先关闭再审查，或遗漏明确的用户验收关口 |

对每个案例报告通过、失败或未执行，并区分人工顺序推演、实际代理运行和真实平台操作。平台写入验证应在获授权的测试项目中单独进行。
